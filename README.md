# Plan Room

Plan Room is a small web app for finding and tracking land survey plans across Singapore. Survey teams think in places ("the Punggol job from last year") but files are usually organised by project number, so this tool lets you narrow plans by town, survey type, date and workflow stage, see them on a map, open a plan's details, and download the filtered set as CSV. It was built as a portfolio project for an internship on land survey project management software.

**Live site:** https://Jeff-rey13.github.io/Project-1/


## Synthetic data

All data in this app is synthetic and generated by `supabase/schema.sql`. No real HDB survey plans are used, and the project is not affiliated with HDB.

## Stack

- Vite, vanilla JavaScript (ES modules), plain CSS with custom properties
- Supabase (Postgres) for data, read-only over the public REST API
- Leaflet 1.9 with OneMap GreyLite tiles from the Singapore Land Authority
- proj4 for WGS84 to SVY21 (EPSG:3414) conversion
- Archivo Variable via Fontsource

No framework, no CSS framework, no UI kit, no chart or icon library.

## Features

- Search by plan number or block, debounced and sanitised
- Filter by survey type, date range, town and workflow stage
- Town list doubles as a bar chart of counts
- Workflow stages bar showing where plans are sitting across the five stages
- Map with markers coloured by survey type, a legend, a metric scale bar, and a live SVY21 coordinate readout under the cursor
- Sortable results table with a details panel styled like a drawing title block
- CSV export of exactly the filtered set, with formula-injection protection

## Local setup

1. Create a Supabase project.
2. In the Supabase dashboard, open the SQL Editor and run `supabase/schema.sql`. This creates the table, enables row level security, and seeds 240 synthetic plans.
3. Copy the project URL and publishable key into `.env.local` at the repository root:

```
VITE_SUPABASE_URL=https://<project>.supabase.co
VITE_SUPABASE_PUBLISHABLE_KEY=sb_publishable_...
```

4. Install and run:

```bash
npm install
npm run dev
```

`.env.local` is gitignored and must never be committed.

## Deployment

Pushing to `main` triggers `.github/workflows/deploy.yml`, which builds the site and publishes it to GitHub Pages.

Two settings are required on the GitHub repository:

- Settings > Pages > Source: GitHub Actions
- Settings > Secrets and variables > Actions > Variables: add `VITE_SUPABASE_URL` and `VITE_SUPABASE_PUBLISHABLE_KEY`

These are repository **variables**, not secrets. Vite inlines any `VITE_` value into the client bundle at build time, so the publishable key is public by design. That is safe here because of the access model described below.

## Security considerations

### What is protected

- **Row level security is on, with a select-only policy.** `survey_plans` has RLS enabled and exactly one policy, granting `select` to `anon` and `authenticated`. No insert, update or delete policy exists, so the public API cannot change data.
- **Only the publishable key is ever used.** It is read through `import.meta.env` and never hard-coded. The secret and service role keys do not appear in the code, the repository or the build.
- **Search input is sanitised.** User input passes through `clean()` in `src/api.js`, which strips everything outside letters, digits, spaces and hyphens and caps length at 50 characters, before it is used in a PostgREST `.or()` filter. Raw input is never interpolated into a filter string.
- **No HTML injection paths.** All data is rendered with `textContent` and DOM nodes. `innerHTML` and `insertAdjacentHTML` are not used anywhere. The only raw HTML string in the app is the static OneMap attribution required by SLA.
- **CSV formula injection is neutralised.** Cells beginning with `=`, `+`, `-`, `@`, tab or carriage return are prefixed with a single quote before export, so a crafted value cannot execute when the file is opened in Excel.
- **External links** use `rel="noopener noreferrer"`.

### Verifying the write protection

A write attempt with the public key should be rejected:

```bash
curl -X POST "https://<project>.supabase.co/rest/v1/survey_plans" -H "apikey: <publishable key>" -H "Content-Type: application/json" -d '{"plan_id":"TEST"}'
```

### What is deliberately out of scope

This is a public read-only demo over synthetic data, so it has no authentication, no accounts or roles, no write path of any kind, and no audit trail. None of these are oversights; they are the scope boundary that keeps a read-only demo honest.

### What a production version would need

If this held real survey records rather than synthetic ones, it would need:

- **SSO** through the agency identity provider, rather than open public access.
- **Town-based and role-based access control**, enforced in RLS policies keyed to the signed-in user, so a surveyor sees only the towns and projects they are assigned.
- **An audit log** of reads and exports, since knowing who pulled which plans matters as much as who changed them.
- **Government-managed hosting** on approved infrastructure rather than GitHub Pages and a third-party database, with data residency in Singapore.
- **IM8 compliance**, covering the security review, logging and retention, vulnerability management and change control that the standard requires.
- **Server-side export controls**, so bulk CSV extraction is rate limited, logged and attributable.
