# Plan Room

A web tool for finding and tracking land survey plans across Singapore, built as a portfolio project for an internship in land survey project management software.

**Live:** https://jeff-rey13.github.io/Project-1/

All data is synthetic and generated by `supabase/schema.sql`. No real HDB survey plans are used, and this project is not affiliated with HDB.

## The problem

Survey teams run several parallel workflows: engineering topographic surveys, 3D LiDAR interior scans, and recess area surveys. Each plan moves through five stages from Requested to Approved.

The filing problem is a mismatch in how people index the work. Files are organised by project number, but people remember jobs by place and time: "the Punggol job from last year", "that recess survey near Blk 512". Finding one plan usually means asking whoever filed it.

Plan Room inverts the index. You narrow by town, survey type, date and workflow stage, see the result on a map, open a plan's title block, and export exactly what you filtered as CSV.

## Stack

| Layer | Choice |
|---|---|
| Languages | JavaScript (ES2022 modules), HTML, CSS, SQL, YAML |
| Build | Vite 8 |
| UI | No framework. Plain DOM APIs and CSS custom properties |
| Data | Supabase (PostgreSQL) over its REST API, read only |
| Mapping | Leaflet 1.9 on OneMap GreyLite tiles from the Singapore Land Authority |
| Projection | proj4, WGS84 to SVY21 (EPSG:3414) |
| Type | Archivo Variable, width axis used for hierarchy |
| CI/CD | GitHub Actions to GitHub Pages |

No framework, no CSS framework, no UI kit, no chart library, no icon library, no date library. Around 1,100 lines of JavaScript and 1,100 lines of CSS.

## Why no framework

React would have been the reflexive choice. I skipped it because the requirements did not justify it: one screen, one state object, no routing, no server rendering, no component reuse across pages. The render path is a handful of functions that each rebuild their own container.

What that bought: a bundle whose weight is Leaflet and proj4 rather than a runtime, no abstraction between the code and the DOM, and no dependency treadmill on a project that should still run in two years.

What it cost: I hand wrote the render scheduling and state handling a framework gives you free, and at least one of the bugs below would not have existed under a reconciler. That is a real tradeoff, not a free win.

## Architecture

```
src/
  main.js        state, render orchestration, event wiring
  api.js         Supabase client, query construction
  facets.js      pure functions: client filtering, cross counts, sort
  format.js      dates, numbers, SVY21 projection
  csv.js         CSV export with formula injection protection
  map.js         Leaflet map, markers, coordinate readout, selection
  ui/filters.js  survey type, date range, town list
  ui/stages.js   workflow stage segments
  ui/table.js    results table, sort, pagination
  ui/details.js  title block panel
  ui/sheet.js    mobile filter sheet
  styles/tokens.css  design tokens only
  styles/app.css     layout and components
supabase/schema.sql  table, indexes, RLS policy, synthetic seed
```

Every module stays under 250 lines. When `main.js` crossed that line, I split the mobile sheet out rather than let it grow.

### One state object, two kinds of filter

```js
const state = {
  rows: [], loading: true, error: null,
  server: { types: [], from: '', to: '', query: '', bounds: null },
  client: { towns: [], stages: [] },
  sort: { key: 'survey_date', dir: 'desc' },
  visibleCount: 50, selectedId: null,
}
```

The split between `server` and `client` is the central design decision. Server filters change what is fetched. Client facets are applied in memory over rows already held.

Towns and stages are client side because they are the filters people toggle repeatedly while scanning, and a network round trip per click would make the tool feel slow. Types and dates are server side because they cut the result set hard enough to be worth re-querying, and because pushing them into SQL lets the composite index do the work.

The result is checkable: town and stage clicks re-render with no network request at all, visible in the browser Network tab.

### Faceted counts

Counts follow the rule that a facet does not filter itself:

- Town counts come from rows filtered by stage only
- Stage counts come from rows filtered by town only
- Visible rows are filtered by both

Without this, selecting Bedok would show every other town at zero, and the counts would stop being useful for deciding where to look next.

### Out of order responses

Filters change faster than the network answers, so responses can arrive out of order. Each fetch takes an incrementing request id, and any response whose id is no longer current is discarded:

```js
const id = ++requestId
const data = await fetchPlans(state.server)
if (id !== requestId) return
```

Without this, typing "tam" quickly can leave you looking at the results for "ta".

### Selection integrity

Selection is held as a plan id, not an index or an object reference. When a filter change removes the selected plan from the visible set, the selection clears instead of pointing at a row that is no longer there.

## Coordinate systems

Singapore survey work is done in SVY21 (EPSG:3414), a transverse Mercator projection. Leaflet works in WGS84 latitude and longitude. Surveyors read easting and northing in metres.

Both are needed, so the app carries both: WGS84 for map positioning, SVY21 for anything a surveyor reads or exports.

```js
proj4.defs('EPSG:3414', '+proj=tmerc +lat_0=1.366666666666667 +lon_0=103.8333333333333 ' +
  '+k=1 +x_0=28001.642 +y_0=38744.572 +ellps=WGS84 +units=m +no_defs')
```

The live coordinate readout under the cursor converts on `mousemove`, throttled with `requestAnimationFrame` so it repaints at most once per frame rather than once per mouse event.

## Security

The threat model is narrow and worth stating plainly: a public page holding a database key.

### What protects it

**Row level security, select only.** `survey_plans` has RLS enabled and exactly one policy, granting `select` to `anon` and `authenticated`. No insert, update or delete policy exists, so the public API cannot change data.

Verified rather than assumed:

```
INSERT  rejected, 42501: new row violates row-level security policy
UPDATE  rejected, zero rows affected
DELETE  rejected, zero rows deleted
Row count after all three: 240, unchanged
Supabase security advisors: no findings
```

**The key in the bundle is public by design.** Vite inlines `VITE_` values at build time, so the publishable key ships inside the JavaScript. That is not a leak, it is the model: the key identifies the project, RLS decides what it may do. The secret and service role keys never appear in the code, the repository or the build.

**Input sanitisation.** Search input passes through `clean()` before reaching a PostgREST `.or()` filter, stripping anything outside letters, digits, spaces and hyphens and capping length at 50 characters. Raw input is never interpolated into a filter string.

**No HTML injection surface.** All data renders through `textContent` and DOM nodes. `innerHTML` and `insertAdjacentHTML` appear nowhere, including inside Leaflet tooltips, which accept HTML strings and are an easy place to leak one. The only raw HTML string in the app is the static OneMap attribution required by SLA.

**CSV formula injection.** Cells beginning with `=`, `+`, `-`, `@`, tab or carriage return are prefixed with a single quote before export, so a crafted field cannot execute when the file opens in Excel.

**Fail loudly on misconfiguration.** The deploy workflow checks both Supabase variables before building and stops with a clear message if either is empty. Without that check the build succeeds and publishes a site that loads no data, which is a much worse way to fail.

### What is deliberately out of scope

No authentication, no roles, no write path, no audit trail. These are not oversights. They are the boundary that keeps a public read only demo honest.

### What a production version would need

- SSO through the agency identity provider instead of open access
- Town and role based access control enforced in RLS policies keyed to the signed in user, so a surveyor sees only their assigned work
- An audit log of reads and exports, since who pulled which plans matters as much as who changed them
- Government managed hosting on approved infrastructure with data residency in Singapore, rather than GitHub Pages and a third party database
- IM8 compliance: security review, logging and retention, vulnerability management, change control
- Server side export controls so bulk CSV extraction is rate limited and attributable
- An automated test suite. `facets.js` is written as pure functions specifically so it is unit testable, but no tests are written here

## Accessibility

- Every interactive element has a visible `:focus-visible` outline and is reachable by keyboard
- The results table is a real `<table>` with `<thead>` and `<th>`, not a grid of divs
- The details panel is `role="dialog"`, moves focus into itself, and closes on Escape
- Colour is never the only signal: survey type always carries its name next to its swatch
- Caps labels come from CSS `text-transform`, so screen readers announce "Survey type" rather than spelling it out
- `prefers-reduced-motion` disables transitions, the loading pulse, and the map fly to animation
- Touch targets are at least 44px on mobile

## Performance

- Markers render to canvas (`preferCanvas: true`) rather than as individual DOM nodes
- The marker layer rebuilds only when the visible row set actually changes, guarded by a comparison of row ids
- Search is debounced at 300ms
- The table paginates at 50 rows
- Postgres carries three indexes matched to the query shapes: a composite on `(town, survey_type, status)`, a descending index on `survey_date` for the default sort, and one on `(lat, lon)` for map bounds queries

## Two bugs worth recording

**The mobile filter sheet did nothing.** The sheet cloned the sidebar with `cloneNode(true)`, which copies markup but drops event listeners. Type chips and date inputs were re-wired afterwards; town rows were not, so tapping a town silently closed the sheet without filtering anything. The fix was not to re-wire more carefully but to stop cloning: the sheet now moves the real sidebar nodes into itself and moves them back on close, so their existing wiring and live counts keep working and no duplicate DOM ids are created.

**A CSS specificity collision.** In the mobile layout, `.plans-table tr { display: block }` and `.table-row { display: grid }` both matched the same element. The first has one class plus one type selector and therefore wins, so the grid layout silently never applied. Scoping the rule to `.plans-table .table-row` fixed it. Worth recording because nothing errors: the layout is simply wrong, and only reading computed styles finds it.

## Design

The interface is built as a survey console: a dark command bar holding search and the workflow stages, a filters rail, a landscape map, and a dense attribute table where every row carries a colour rule in its survey type.

Colour is functional rather than decorative. Three survey type colours follow topographic map convention (contour brown, blue, green), each at 5:1 contrast or better on white. A single accent, flagging tape pink, is reserved for selection and focus and appears nowhere else. Type is one family, Archivo, using its variable width axis for hierarchy so a second typeface is unnecessary.

Design tokens live in `tokens.css` and nowhere else, which is enforceable rather than aspirational:

```bash
grep -rnE "#[0-9A-Fa-f]{6}" src --include=*.js --include=app.css   # returns nothing
```

## Local setup

Requires Node 22 or later.

```bash
git clone https://github.com/Jeff-rey13/Project-1.git
cd Project-1
npm install
```

Create a Supabase project, run `supabase/schema.sql` in the SQL editor (it creates the table, enables RLS and seeds 240 synthetic plans), then create `.env.local` in the repository root:

```
VITE_SUPABASE_URL=https://<project>.supabase.co
VITE_SUPABASE_PUBLISHABLE_KEY=<publishable key>
```

```bash
npm run dev      # development server
npm run build    # production build
npm run preview  # serve the production build
```

`.env.local` is gitignored and must never be committed.

## Deployment

Pushing to `main` runs `.github/workflows/deploy.yml`, which checks the Supabase configuration, builds, and publishes to GitHub Pages.

Two repository settings are required:

- Settings > Pages > Source: GitHub Actions
- Settings > Secrets and variables > Actions > Variables: `VITE_SUPABASE_URL` and `VITE_SUPABASE_PUBLISHABLE_KEY`

These belong under Variables rather than Secrets, because the workflow reads them through the `vars` context.
